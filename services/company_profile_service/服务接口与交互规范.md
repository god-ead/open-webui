# 企业画像服务接口与交互规范

## 1. 文档目的

本文档定义企业画像服务与调用方之间的实际接口和交互方式，作为双方联调、服务实现和验收的统一规范。

本文档只描述服务行为，不约束内部代码结构、数据库、队列或部署方式。

## 2. 交互总览

企业画像服务对外包含以下业务交互：

1. 调用方提交企业画像任务，服务立即返回受理结果。
2. 调用方使用 `task_id` 主动查询任务状态。
3. 任务成功后，调用方使用结果中的地址下载 PDF。
4. 任务成功后，服务向本次请求指定的 `callback` 地址发送加密回调。

```text
调用方 POST /api/task
  ├─ 请求不合法 → HTTP 400/422，任务不创建
  └─ 请求合法 → HTTP 200 + queued + task_id
                    ↓
               异步处理任务
                    ↓
          ┌─────────┴─────────┐
          │                   │
    调用方随时 GET       任务成功后服务 POST
    /api/status/{id}      请求中的 callback 地址
          │                   │
   查询/PDF/成功回调       发送加密 task_id + pdfurl
```

各项交互通过同一个 `task_id` 关联。

## 3. 任务提交接口

### 3.1 请求

```text
POST /api/task
Content-Type: application/json
```

请求示例：

```json
{
  "task_type": "profile",
  "callback": "http://172.19.59.163:8096/api/CompanyProfile/ProfileCallback",
  "input": {
    "company_name": "可孚医疗科技股份有限公司"
  }
}
```

字段说明：

| 字段 | 类型 | 必填 | 规则 |
|---|---|---|---|
| `task_type` | string | 是 | 去除首尾空白后不能为空；当前企业画像服务只接受 `profile` |
| `callback` | string | 是 | 当前任务成功后的实际回调地址，必须是合法 HTTP/HTTPS URL |
| `input` | object | 是 | 必须是非空 JSON 对象 |
| `input.company_name` | string | 是 | 公司全称，去除首尾空白后不能为空 |

请求中未声明的额外顶层字段当前会被忽略。

### 3.2 受理成功响应

请求成功受理时返回 HTTP `200 OK`：

```json
{
  "task_id": "77686774-b327-41ce-9554-848ff0cdc01c",
  "status": "queued",
  "queue_position": 1,
  "created_at": "2026-06-26T12:51:27.315279"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 服务生成的任务 UUID，后续查询和回调均使用该值 |
| `status` | string | 固定为 `queued` |
| `queue_position` | integer | 任务受理时的位置参考值，不代表后续实时排名 |
| `created_at` | string | 任务创建时间，格式与当前接口响应保持一致 |

受理成功只表示任务已经创建，不表示企业画像已经生成完成。

### 3.3 请求错误

| 场景 | HTTP 状态码 |
|---|---|
| 缺少 `task_type`、`input` 或 `callback` | `422 Unprocessable Entity` |
| `task_type` 为空或只有空白字符 | `422 Unprocessable Entity` |
| `input` 不是 JSON 对象或是空对象 | `422 Unprocessable Entity` |
| `callback` 为 `null` 或不是合法 HTTP/HTTPS URL | `422 Unprocessable Entity` |
| `task_type` 不是 `profile` | `400 Bad Request` |

API Gateway 只校验 `input` 是否存在且非空，不识别 `company_name` 等业务字段。当 input 非空但 `company_name` 缺失、不是字符串、为空或只有空白字符时，任务在企业画像业务处理阶段进入 `failed`，并通过状态查询返回`output.code=2`业务错误。
不支持的任务类型响应示例：

```json
{
  "detail": "不支持的任务类型: profile2。支持的类型: profile"
}
```

## 4. 任务状态查询接口

### 4.1 请求

调用方可以在任务排队、处理、完成或失败后随时查询。

```text
GET /api/status/{task_id}
```

示例：

```bash
curl "http://ip:port/api/status/77686774-b327-41ce-9554-848ff0cdc01c"
```

调用方应原样使用任务提交接口返回的 UUID。

任务不存在时返回：

```text
HTTP 404 Not Found
```

```json
{
  "detail": "任务不存在"
}
```

### 4.2 状态取值

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `queued` | 已受理，等待处理 | 否 |
| `processing` | 正在生成企业画像 | 否 |
| `completed` | 企业画像和 PDF 已成功生成 | 是 |
| `failed` | 任务处理失败 | 是 |

正常状态流转：

```text
queued → processing → completed
                    └→ failed
```

发生服务恢复时，处于 `processing` 的任务可能重新变为 `queued` 并再次处理。调用方应以每次查询返回的最新状态为准。

### 4.3 查询响应

成功任务示例：

```json
{
  "task_id": "77686774-b327-41ce-9554-848ff0cdc01c",
  "task_type": "profile",
  "input": {
    "company_name": "可孚医疗科技股份有限公司"
  },
  "status": "completed",
  "output": {
    "code": 0,
    "message": "success",
    "timestamp": "20260626205358",
    "data": {
      "profile": "http://ip:port/api/download/77686774-b327-41_20260626_205358_8b1d4cab.pdf",
      "version": "1.0"
    }
  },
  "error_msg": null,
  "worker_id": "service-1",
  "queue_position": 1,
  "processing_time": 150.919,
  "created_at": "2026-06-26 20:51:27",
  "started_at": "2026-06-26 20:51:27",
  "completed_at": "2026-06-26 20:53:58"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 任务 UUID |
| `task_type` | string | 企业画像任务为 `profile` |
| `input` | object | 提交任务时的原始输入 |
| `status` | string | 当前任务状态 |
| `output` | object/null | 业务输出；尚未产生输出时通常为 `null` |
| `error_msg` | string/null | 原始失败原因；非失败状态通常为 `null` |
| `worker_id` | string/null | 执行任务的 Worker 标识；尚未开始处理时通常为 `null` |
| `queue_position` | integer | 任务受理时保存的位置参考值，不是实时排名 |
| `processing_time` | number/null | 已记录的处理耗时，单位为秒 |
| `created_at` | string/null | 任务创建时间，格式为 `yyyy-MM-dd HH:mm:ss` |
| `started_at` | string/null | 任务开始时间，格式为 `yyyy-MM-dd HH:mm:ss` |
| `completed_at` | string/null | 任务结束时间，格式为 `yyyy-MM-dd HH:mm:ss` |

状态查询中的三个时间字段格式为 `yyyy-MM-dd HH:mm:ss`，没有毫秒、`T` 或时区后缀。该格式与任务提交响应中的 `created_at` 不同。

## 5. 业务输出规范

### 5.1 output 结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | integer | 成功固定为 `0` |
| `message` | string | 业务结果描述，成功时为 `success` |
| `timestamp` | string | 结果生成时间，格式为 `yyyyMMddHHmmss` |
| `data.profile` | string | PDF 下载地址 |
| `data.version` | string | 企业画像结果版本；当前为 `1.0` |

### 5.2 业务状态码

| code | 含义 | `message` 格式 |
|---|---|---|
| `0` | 企业画像生成成功 | `success` |
| `1` | 大模型服务调用异常 | `大模型调用异常: {具体错误}` |
| `2` | 配置、企业数据或输入等业务调用失败 | `调用失败: {具体错误}` |
| `3` | 任务超时、PDF 生成或其他企业画像生成异常 | `企业画像生成失败: {具体错误}` |

HTTP 请求受理成功和业务处理成功是不同概念：

- `POST /api/task` 返回 HTTP 200，表示任务已受理。
- `output.code=0` 且 `status=completed` 表示最终成功。
- `status=failed` 表示最终失败；失败任务不发送 callback 回调。

### 5.3 成功输出

```json
{
  "code": 0,
  "message": "success",
  "timestamp": "20260626205358",
  "data": {
    "profile": "http://ip:port/api/download/{file_name}",
    "version": "1.0"
  }
}
```

### 5.4 失败输出

```json
{
  "code": 2,
  "message": "调用失败: input.company_name 不能为空",
  "timestamp": "20260714103000",
  "data": {
    "profile": "",
    "version": ""
  }
}
```

当前服务产生的失败输出中，`data.profile` 和 `data.version` 为空字符串。

## 6. PDF 下载接口

成功任务的 `output.data.profile` 返回 PDF 下载地址：

```text
GET /api/download/{file_name}
```

文件名格式：

```text
{task_id前16位}_{yyyyMMdd}_{HHmmss}_{8位UUID}.pdf
```

下载成功时：

- 返回 HTTP `200 OK`。
- `Content-Type` 为 `application/pdf`。
- 使用请求中的文件名作为下载文件名。

| 失败场景 | HTTP 状态码 | `detail` |
|---|---|---|
| 文件名非法或文件不存在 | `404 Not Found` | `文件不存在` |
| 文件已超过下载有效期 | `404 Not Found` | `文件已过期` |

当前 PDF 下载有效期为 24 小时，从文件修改时间计算。调用方应在任务完成后尽快下载；超过有效期后，无法继续下载。

## 7. 企业画像成功回调

### 7.1 触发行为

任务成功完成、已生成非空 PDF 下载地址且提交任务时提供了回调地址时，服务向本次请求中的 `callback` 地址发送回调。

任务失败时不发送回调。调用方应通过 `GET /api/status/{task_id}` 获取失败状态和原因。

### 7.2 回调请求

```text
POST {callback}

token: <token密文Base64>
Content-Type: application/json

<Body密文Base64>
```

Body 为紧凑 JSON，内容如下：

```json
{"task_id":"77686774-b327-41ce-9554-848ff0cdc01c","pdfurl":"http://ip:port/api/download/77686774-b327-41_20260626_205358_8b1d4cab.pdf"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 当前任务 ID |
| `pdfurl` | string | 当前任务生成的 PDF 下载地址 |

token 同样为紧凑 JSON，内容如下：

```json
{"IP":"172.19.xx.xx","date":"2026-07-14 10:30"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `IP` | string | 服务提供方与调用方约定的服务 IP 标识 |
| `date` | string | 回调发送时间，格式为 `yyyy-MM-dd HH:mm` |

### 7.3 加密规则

| 项目 | Body | token |
|---|---|---|
| 算法 | AES | AES |
| 模式 | CBC | CBC |
| 填充 | PKCS7，块大小 128 bit | PKCS7，块大小 128 bit |
| KEY/IV | BODY KEY/IV | TOKEN KEY/IV |
| KEY/IV 长度 | UTF-8 编码后 16 字节 | UTF-8 编码后 16 字节 |
| 明文编码 | UTF-8 | UTF-8 |
| 密文编码 | 标准 Base64 ASCII | 标准 Base64 ASCII |

KEY、IV 和密文属于敏感信息，不应写入日志或文档。

## 8. 回调响应与成功判定

调用方返回的 response body 使用 BODY KEY/IV，按照与请求 Body 相同的 AES-CBC、PKCS7、Base64 规则加密。

解密后的响应应为 JSON 对象：

```json
{"code":0,"msg":"操作成功"}
```

一次发送同时满足以下条件才视为成功：

1. HTTP 状态码为 2xx。
2. response body 是合法 Base64。
3. response body 能使用 BODY KEY/IV 成功解密。
4. 解密结果是合法 JSON 对象。
5. JSON 对象中的 `code` 等于数值 `0`。

服务只使用 `code` 判断成功，不检查 `msg`。字符串 `"0"` 不会被视为成功，因此调用方应返回 JSON 数值 `0`。

## 9. 回调超时、重试与幂等

当前回调客户端超时参数为 30 秒。该参数用于单次发送的网络阶段，不是整个多次发送过程的总时长上限。

当前回调行为为：首次发送失败后最多重试 3 次，总计最多发送 4 次。

```text
第 1 次发送失败 → 等待 5 秒
第 2 次发送失败 → 等待 10 秒
第 3 次发送失败 → 等待 15 秒
第 4 次发送失败 → 停止
```

以下情况会触发重试：

- 网络连接异常或超时。
- HTTP 状态码不是 2xx。
- Base64 解码、AES 解密、去填充或 UTF-8 解码失败。
- 解密结果不是合法 JSON 对象。
- 响应 `code` 不等于数值 0。

回调最终失败不会改变已经完成的任务状态。调用方仍可通过状态查询获得 `completed` 状态和 PDF 地址。

当前服务在上述发送全部失败后不会继续进行延迟补发。由于一次成功任务可能收到多次回调，调用方必须使用 `task_id` 作为幂等键。

## 10. 调用方接入要求

1. 保存任务提交返回的 `task_id`。
2. 不要把 HTTP 200 受理成功当作企业画像生成成功。
3. 使用状态查询接口获取最终结果和失败原因。
4. 未收到成功回调时，使用状态查询接口兜底。
5. 失败任务不会收到 HTTP 回调。
6. 使用 `task_id` 对成功回调进行处理。
7. 在 PDF 下载有效期内完成下载。
8. 回调接口返回加密响应，并确保解密后的 `code` 是 JSON 数值 `0`。
