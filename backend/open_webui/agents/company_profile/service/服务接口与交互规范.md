# 企业画像服务接口与交互规范

## 1. 文档目的

本文档定义企业画像服务与调用方之间的目标接口和交互方式，作为双方联调、服务实现和验收的统一规范。

本文档只描述服务行为，不约束内部代码结构、数据库、队列或部署方式。

## 2. 交互总览

企业画像服务对外包含三种交互：

1. 调用方提交任务，服务立即返回任务受理结果。
2. 调用方使用 `task_id` 主动查询任务状态。
3. 任务成功生成 PDF 后，服务向请求中的 `callback` 地址主动发送加密回调。

```text
调用方 POST /api/task
  ├─ 请求不合法 → HTTP 400/422，任务不创建
  └─ 请求合法 → 返回 queued + task_id
                    ↓
               异步处理任务
                    ↓
          ┌─────────┴─────────┐
          │                   │
    调用方随时 GET       任务成功后服务 POST
    /api/status/{id}      请求中的 callback 地址
          │                   │
    获取完整任务状态       发送加密 task_id + pdfurl
```

三种交互通过同一个 `task_id` 关联。

## 3. 任务提交接口

### 3.1 请求

```text
POST /api/task
Content-Type: application/json
```

请求体：

```json
{
  "task_type": "profile",
  "callback": "http://172.19.59.163:8096/api/CompanyProfile/ProfileCallback",
  "input": {
    "company_name": "可孚医疗科技股份有限公司"
  }
}
```

字段说明：

| 字段 | 类型 | 必填 | 规则 |
|---|---|---|---|
| `task_type` | string | 是 | 只能为 `profile` |
| `callback` | string | 是 | 本任务成功后的实际回调地址，必须是合法 HTTP/HTTPS URL |
| `input` | object | 是 | 企业画像任务输入 |
| `input.company_name` | string | 是 | 公司全称，由企业画像业务处理阶段校验 |

服务必须使用本次请求中的 `callback` 地址发送成功回调，不得使用其他固定地址替代。

### 3.2 受理成功响应

请求校验通过后，服务创建任务并立即响应，不等待企业画像生成完成。

```json
{
  "task_id": "77686774-b327-41ce-9554-848ff0cdc01c",
  "status": "queued",
  "queue_position": 1,
  "created_at": "2026-06-26T12:51:27.315279"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 任务唯一标识，后续查询和回调均使用该值 |
| `status` | string | 固定为 `queued` |
| `queue_position` | integer | 提交时的队列位置 |
| `created_at` | string | 任务创建时间，格式与当前接口响应保持一致 |

受理成功只表示任务已创建并进入异步处理流程，不表示任务已经完成。

### 3.3 输入错误响应

输入校验失败时，服务不得创建任务，不得写入任务队列，也不得发送回调。

| 场景 | HTTP 状态码 |
|---|---|
| `task_type` 不是 `profile` | `400 Bad Request` |
| 缺少顶层字段 `task_type`、`input` 或 `callback` | `422 Unprocessable Entity` |
| `input` 是空对象 | `422 Unprocessable Entity` |
| `callback` 不是合法 HTTP/HTTPS URL | `422 Unprocessable Entity` |

API Gateway 只校验 `input` 是否存在且非空，不识别 `company_name` 等业务字段。当 input 非空但 `company_name` 缺失、不是字符串、为空或只有空白字符时，任务在企业画像业务处理阶段进入 `failed`，并通过状态查询返回业务错误。

不支持的任务类型示例：

```json
{
  "detail": "不支持的任务类型: profile2。支持的类型: profile"
}
```

## 4. 任务状态查询接口

### 4.1 请求

调用方可以在任务排队、处理、完成或失败后随时查询。

```text
GET /api/status/{task_id}
```

示例：

```bash
curl "http://ip:port/api/status/77686774-b327-41ce-9554-848ff0cdc01c"
```

任务不存在时返回：

```text
HTTP 404 Not Found
```

### 4.2 状态取值

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `queued` | 已受理，等待处理 | 否 |
| `processing` | Worker 正在处理 | 否 |
| `completed` | 企业画像和 PDF 已成功生成 | 是 |
| `failed` | 任务处理失败 | 是 |

状态转换：

```text
queued → processing → completed
                    └→ failed
```

### 4.3 查询响应

```json
{
  "task_id": "77686774-b327-41ce-9554-848ff0cdc01c",
  "task_type": "profile",
  "input": {
    "company_name": "可孚医疗科技股份有限公司"
  },
  "status": "completed",
  "output": {
    "code": 0,
    "message": "success",
    "timestamp": "20260626205358",
    "data": {
      "profile": "http://ip:port/api/download/77686774-b327-41_20260626_205358_8b1d4cab.pdf",
      "version": "1.0"
    }
  },
  "error_msg": null,
  "worker_id": "service-1",
  "queue_position": 1,
  "processing_time": 150.919,
  "created_at": "2026-06-26 20:51:27",
  "started_at": "2026-06-26 20:51:27",
  "completed_at": "2026-06-26 20:53:58"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 任务唯一标识 |
| `task_type` | string | 固定为 `profile` |
| `input` | object | 原始任务输入 |
| `status` | string | 当前任务状态 |
| `output` | object/null | 业务输出；任务尚未产生输出时可为 `null` |
| `error_msg` | string/null | 失败原因；非失败状态通常为 `null` |
| `worker_id` | string/null | 执行任务的 Worker 标识 |
| `queue_position` | integer | 提交时的队列位置 |
| `processing_time` | number/null | 处理耗时，单位为秒 |
| `created_at` | string | 任务创建时间，格式为 `yyyy-MM-dd HH:mm:ss` |
| `started_at` | string/null | 任务开始时间，格式为 `yyyy-MM-dd HH:mm:ss` |
| `completed_at` | string/null | 任务结束时间，格式为 `yyyy-MM-dd HH:mm:ss` |

## 5. 业务输出规范

### 5.1 output 结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | integer | 业务状态码 |
| `message` | string | 业务结果描述 |
| `timestamp` | string | 服务器时间，格式为 `yyyyMMddHHmmss` |
| `data.profile` | string | 成功时为 PDF 下载地址；失败时为空字符串 |
| `data.version` | string | 接口或处理逻辑版本号 |

### 5.2 业务状态码

| code | 含义 | message 格式 |
|---|---|---|
| `0` | 企业画像生成成功 | `success` |
| `1` | 大模型调用异常 | `大模型调用异常: {具体错误}` |
| `2` | 配置、企业、输入等业务调用失败 | `调用失败: {具体错误}` |
| `3` | 超时或其他企业画像生成异常 | `企业画像生成失败: {具体错误}` |

HTTP 请求受理成功与业务处理成功是两个不同概念：

- `POST /api/task` 成功表示任务已受理。
- `output.code=0` 且 `status=completed` 表示企业画像最终生成成功。

## 6. PDF 下载接口

成功任务的 `output.data.profile` 返回 PDF 下载地址：

```text
GET /api/download/{file_name}
```

文件名格式：

```text
{task_id前16位}_{yyyyMMdd_HHmmss}_{8位UUID}.pdf
```

调用方应在任务完成后的 24 小时内下载 PDF。

| HTTP 状态码 | 含义 |
|---|---|
| `200 OK` | 文件存在且未过期，返回 PDF |
| `404 Not Found` | 文件不存在或文件名非法 |

PDF 超过有效期后不再提供下载，本规范不额外约定 `410 Gone` 等过期专用状态码。

## 7. 成功回调接口

### 7.1 触发条件

只有同时满足以下条件时，企业画像服务才发送回调：

1. 任务类型为 `profile`。
2. 任务状态为 `completed`。
3. `output.code=0`。
4. `output.data.profile` 包含有效 PDF 下载地址。
5. 任务请求包含有效的 `callback` 地址。

任务状态为 `failed` 时不发送回调。调用方应通过 `GET /api/status/{task_id}` 查询失败状态、业务码和错误信息。

每个成功任务只能使用企业画像专用加密回调机制，不得再额外发送普通 JSON 回调。

### 7.2 回调唯一性与内部状态通知

请求中的 `callback` 是必填的真实回调地址，由企业画像专用加密回调使用。

profile 成功任务写入内部结果队列时，必须携带请求中的真实 `callback` 和业务生成的明文 `callback_payload`。API Gateway 根据部署配置完成加密和发送，且不得再发送第二套普通 JSON 回调。失败任务的 `callback` 必须为 `null`。

```text
成功结果队列：callback + callback_payload → API Gateway 加密并发送
失败结果队列：callback=null → 只通知状态
```

### 7.3 回调地址

服务必须向该任务在 `POST /api/task` 请求中提供的 `callback` 地址发送回调。

### 7.4 回调请求

```text
POST {callback}

Headers:
token: <encrypted_token_base64>
Content-Type: application/json

Body:
<encrypted_body_base64>
```

Body 必须是加密后的原始 Base64 字符串，不得再包装成 JSON 对象。

### 7.5 Body 明文

```json
{
  "task_id": "77686774-b327-41ce-9554-848ff0cdc01c",
  "pdfurl": "http://ip:port/api/download/77686774-b327-41_20260626_205358_8b1d4cab.pdf"
}
```

字段只包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 当前任务 ID |
| `pdfurl` | string | 当前任务生成的 PDF 下载地址 |

### 7.6 token 明文

```json
{
  "IP": "172.19.45.13",
  "date": "2026-07-10 10:30"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `IP` | string | 企业画像服务所在服务器 IP |
| `date` | string | 当前时间，格式为 `yyyy-MM-dd HH:mm` |

### 7.7 加密规则

Body 和 token 分别使用双方约定的 KEY/IV 加密：

| 项目 | Body | token |
|---|---|---|
| 算法 | AES | AES |
| 模式 | CBC | CBC |
| 填充 | PKCS7 | PKCS7 |
| 密钥长度 | 128 bits | 128 bits |
| 字符编码 | UTF-8 | UTF-8 |
| 输出格式 | Base64 | Base64 |
| KEY/IV | BODY KEY/IV | TOKEN KEY/IV |

KEY、IV、请求密文不得完整写入日志或接口文档。

## 8. 回调响应与成功判定

### 8.1 响应格式

对方回调接口返回的 response body 使用 BODY KEY/IV，按照与请求 Body 相同的 AES-CBC-PKCS7-Base64 规则加密。

解密后的响应结构：

```json
{
  "code": 0,
  "msg": "操作成功"
}
```

### 8.2 成功条件

一次回调必须同时满足以下条件才算成功：

1. HTTP 状态码为 2xx。
2. response body 能使用 BODY KEY/IV 成功解密。
3. 解密结果是合法 JSON。
4. 解密结果中的 `code` 等于 `0`。

任何一项不满足，均视为本次回调失败。

## 9. 回调重试

成功任务的回调最多发送 3 次：

```text
第 1 次发送失败 → 记为第 1 次失败
第 2 次发送失败 → 记为第 2 次失败
第 3 次发送失败 → 记为第 3 次失败，停止发送
```

也就是说，首次发送包含在最多 3 次发送次数内，不是“首次发送 + 额外重试 3 次”。

以下情况均应触发再次发送：

- 网络连接异常或超时。
- HTTP 状态码不是 2xx。
- response body 无法解密。
- 解密结果不是合法 JSON。
- 解密结果中的 `code` 不等于 `0`。

重试间隔可以由服务配置，但不得改变“单个成功任务最多发送 3 次”的对外语义。

回调最终失败时：

- 记录每次发送结果和最终失败原因。
- 不得把已经成功的企业画像任务改为 `failed`。
- 调用方仍可通过状态查询接口获得 `completed` 状态和 PDF 地址。

由于回调可能重复发送，调用方必须以 `task_id` 作为幂等键，避免重复处理同一个成功任务。

## 10. 日志与安全要求

服务应记录：

- `task_id`
- `pdfurl`
- `callback` 地址
- 每次回调的发送序号
- HTTP 状态码
- 解密后的业务 `code`，但不记录敏感明文
- 回调成功或失败
- 异常原因

服务不得在日志中完整记录：

- BODY KEY/IV
- TOKEN KEY/IV
- token 密文
- 请求 Body 密文

## 11. 接口关系总结

| 交互 | 发起方 | 接收方 | 发生时间 | 结果 |
|---|---|---|---|---|
| 任务提交 | 调用方 | 企业画像服务 | 任务开始前 | 返回 `queued + task_id` 或输入错误 |
| 状态查询 | 调用方 | 企业画像服务 | 任务创建后的任意时间 | 返回当前状态和完整任务结果 |
| 成功回调 | 企业画像服务 | 请求中的 `callback` 地址 | PDF 成功生成后 | 发送加密的 `task_id + pdfurl` |

任务失败时不发送回调。状态查询是调用方获取失败结果以及回调未收到时的兜底机制。
